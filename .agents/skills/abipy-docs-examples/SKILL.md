# Develop AbiPy documentation and examples

Document the public behavior implemented in code and keep examples executable, small, and scientifically honest.
Do not use documentation changes to conceal an unclear API; improve the library interface first when needed.

Use `abipy-plotting` for plotting API conventions, `abipy-flowtk` for workflow examples, `abipy-cli` for command
references, and `abipy-reference-data` for bundled example inputs.

## Know maintained sources from generated output

The main maintained documentation sources are under `docs/`, with `docs/index.rst` defining the top-level toctrees.
Important areas include:

- `docs/tutorials`, `docs/workflows`, and topical `.rst` pages for narrative guides;
- `docs/scripts` for command-line documentation;
- `docs/abiref.bib` for citations and `docs/links.rst` for global substitutions/links;
- `abipy/examples/plot` and `abipy/examples/flows` for executable gallery sources;
- Python docstrings for API reference content.

`docs/api` is regenerated by `sphinx-apidoc`. `docs/gallery` and `docs/flow_gallery` are generated by Sphinx Gallery.
Edit the Python modules, docstrings, example sources, or generator configuration—not generated gallery pages. When
tracked API stubs change, regenerate them through the established command instead of hand-maintaining a module list.

Before editing or regenerating, check the working tree so generated output does not overwrite unrelated user work.

## Write narrative documentation

Follow the surrounding reStructuredText style and add a new page to the appropriate `toctree`; an unreferenced page
may build but remain undiscoverable. Give stable sections explicit labels when other pages should link to them.

Prefer semantic Sphinx roles and cross-references over literal names and raw URLs:

- Python objects: `:class:`, `:meth:`, `:func:`, `:mod:`;
- documents and sections: `:doc:` and `:ref:`;
- commands and files: `:program:` and `:file:`;
- citations: `:cite:` with an entry in `docs/abiref.bib`.

Reuse aliases already defined in `docs/links.rst`. Add a global alias only when several pages benefit; otherwise keep
the link local. Use notes and warnings for consequential information, not ordinary prose.

Keep commands copyable and specify their working directory, required environment, and whether they write files,
launch programs, submit jobs, or use the network. Do not document a destructive or scheduler command as though it
were an inspection command.

## Docstrings and API pages

AbiPy docstrings use Google-style sections interpreted by Napoleon. Document public parameters, units, shapes,
return values, exceptions, side effects, optional dependencies, and index conventions that are not obvious from the
signature. Keep examples short enough for the docstring; move complete workflows to the gallery.

New public modules are discovered by the `sphinx-apidoc` command used in `tasks.py`. The generated API excludes
tests, benchmarks, data, integration tests, test files, and examples. If a public object is intentionally exported,
also follow the package's `__all__` or public-import convention so autodoc and users see the same API.

Regenerate API stubs with the command encoded in `tasks.py` or with `invoke make-doc` only when an interactive full
workflow is desired. `invoke make-doc` also cleans, builds, and opens the HTML site in a browser, so it is not the
preferred headless verification command.

## CLI documentation

CLI pages under `docs/scripts` normally combine narrative examples with the `sphinxarg.ext` directive:

```rst
.. argparse::
   :ref: abipy.scripts.abiopen.get_parser
   :prog: abiopen.py
```

Keep the parser importable without executing the command, opening a GUI, accessing the network, or requiring an
optional runtime dependency. Use `.. command-output::` only for deterministic, fast, read-only commands available in
the documentation environment.

Update the scripts toctree when adding a maintained CLI page. The parser's own help remains the source of truth for
the complete option list; narrative docs should explain workflows and important safety constraints rather than
duplicate every flag manually.

## Plot gallery examples

Plot examples live in `abipy/examples/plot` and are selected by the gallery filename pattern `plot*`. Start with a
raw reStructuredText module docstring containing a concise title and underline:

```python
r"""
Example title
=============

Explain the scientific question and the data used.
"""
```

Use `# %%` blocks followed by explanatory comments to interleave narrative and executable code. Load bundled inputs
through `abipy.data`, close file-backed objects with context managers, and call public APIs as a user would. Let
Sphinx Gallery capture figures; do not save generated PNG/PDF files in the source directory.

Keep examples deterministic and modest in memory/runtime. Avoid credentials, network downloads, personal paths,
interactive prompts, GUI-only backends, and unavailable external executables. The docs configure Matplotlib `Agg`
and disable Plotly's default show behavior, so examples must not depend on browser display.

Add a new example only when it teaches a distinct workflow. Extend an existing example when the new call is a small
variation of the same concept.

## Flow gallery examples

Flow examples live in `abipy/examples/flows` and are selected by the pattern `run*`. Follow the established split:

- a `build_flow(options)` function creates and returns the graph;
- `@flowtk.flow_main` wraps `main(options)` for normal user execution;
- workdir and manager come from the supplied options;
- bundled structures and pseudos replace machine-specific inputs.

Documentation execution may build, validate, or visualize a graph, but it must not submit calculations. Follow the
nearest maintained `READTHEDOCS` guard for gallery-specific graph generation. Never add `--scheduler`, queue
submission, or cleanup of arbitrary work directories to documentation execution.

Choose minimal meshes/cutoffs when calculations or ABINIT queries cannot be avoided, while preserving the topology
being demonstrated. Clearly label pedagogical parameters that are not suitable for production science.

The full docs Makefile removes `abipy/examples/flows/flow_*` before gallery execution. Treat those as generated flow
directories and verify that no user-owned work is present there before running the full target.

## Build and verification levels

Activate the correct Python environment and install/use the existing `docs` dependency group. Do not install or
upgrade documentation packages implicitly merely because a build reports a missing dependency.

Use verification proportional to the change:

1. Run affected library/CLI tests and execute a new example directly with a headless backend where possible.
2. For prose, docstrings, or API links, build without executing galleries:

   ```bash
   cd docs
   READTHEDOCS=1 sphinx-build -D plot_gallery=0 -b html -d _build/doctrees . _build/html
   ```

3. Regenerate API stubs when public module structure changed.
4. Run the full `make html` from `docs` when gallery execution or full integration matters. It runs
   `generate_rst_files.py`, cleans generated flow directories, and executes gallery examples.
5. Use `make linkcheck` when external links changed, recognizing that it requires network access and can fail for
   reasons outside the repository.

For stricter review, add `-W -n --keep-going` to a focused Sphinx build, but distinguish new warnings caused by the
change from existing project warnings. The normal Makefile does not enable warnings-as-errors.

Do not open the generated site with `open`, a browser, or `invoke make-doc` in a headless agent session. Inspect the
build result and relevant HTML files directly.

## Review generated changes

After a build, inspect `git status` before accepting changes. Do not commit `_build`, gallery caches, notebooks,
images, zip files, flow work directories, or example output artifacts unless the repository intentionally tracks
that exact generated class.

Check that:

- new pages appear in the intended toctree;
- cross-references resolve and code examples match the current API;
- galleries execute without unexpected failures;
- no example submits work or depends on local configuration;
- API regeneration changes only the expected modules;
- generated artifacts have not leaked into source directories.

Report source pages/examples changed, generated API stubs changed, build command and environment, gallery execution
status, new versus pre-existing warnings, and any optional example not executed with the reason.
